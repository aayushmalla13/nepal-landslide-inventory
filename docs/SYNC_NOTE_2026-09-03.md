# Repository state after the 2026-09-03 district-assignment work

Read this before running anything.

## The database on this machine is one step behind the outputs

`data/outputs/` and `data/releases/nepal_landslide_rainfall_v0.3.0_20260903/`
were produced by re-running the pipeline in the analysis environment. The
350 MB working database at `data/raw_sqlite/landslide_inventory.sqlite` could
not be transferred back (the file-transfer path caps individual files well below
that size), so it still holds the pre-2026-09-03 extraction.

Nothing is lost — the pipeline is deterministic. To make this machine
self-consistent, snapshot the database and re-run the stages:

```bash
cp data/raw_sqlite/landslide_inventory.sqlite \
   data/raw_sqlite/landslide_inventory.snapshot_$(date +%Y%m%d)_pre_gazetteer_rerun.sqlite

for s in extract event_specificity location_consistency filter_scope \
         corrections dedup event_typing export_final; do
  PYTHONPATH=src .venv/bin/python -m landslide_inventory.run --stage $s --config config.yaml
done
PYTHONPATH=src .venv/bin/python -m landslide_inventory.run --stage analysis         --config config.yaml
PYTHONPATH=src .venv/bin/python -m landslide_inventory.run --stage rainfall_figures --config config.yaml
PYTHONPATH=src .venv/bin/python -m landslide_inventory.run --stage rainfall_release --config config.yaml
PYTHONPATH=src .venv/bin/python scripts/verify_releases.py
```

Expected end state: 10,203 articles, 6,371 class-1, 2,950 canonical events,
rainfall bundle lock `2658b66a0ff3…`. `rainfall_release` regenerating an
identical bundle from unchanged inputs is allowed and is the check that the
transfer was faithful.

Total runtime in the analysis environment was about 90 seconds for the whole
sequence, extract included.
